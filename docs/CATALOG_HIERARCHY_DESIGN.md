# Проектирование иерархии каталога и реальных прототипов

**Статус:** проектное предложение; не физическая схема БД и не разрешение на импорт данных.  
**База:** `main` после PR #58, commit `6ae1dc8e451b86c1fce59859768e404254e6e8dd`.  
**Цель:** отделить идентичность каталоговых сущностей от их отображения в навигационном дереве.

## 1. Принципы

1. `Casting`, `Release`, `Series`, `Package`, `Brand` и `Manufacturer` остаются самостоятельными сущностями со стабильными внутренними ID.
2. Дерево — способ навигации и группировки, а не источник идентичности. Перемещение узла не меняет ID и не переписывает историю выпуска.
3. Серия и продуктовая линейка — разные понятия. Серия не должна быть вложена в `Release` как обычное текстовое поле; связь `ReleaseSeries` уже существует.
4. Год в дереве — каталоговая группировка. Он не заменяет `Release.catalog_year` и не означает фактическую дату поступления в продажу.
5. Один и тот же выпуск может отображаться в нескольких ветвях каталога, если это нужно для навигации, без дублирования `Release`.
6. Перестановка узлов, изменение подписи и перемещение выпуска должны быть аудитируемыми действиями.
7. Все правила должны учитывать, что разные продуктовые линейки могут иметь разные уровни иерархии.

## 2. Рекомендуемая модель дерева

### `ProductLine` — самостоятельная сущность

Минимальные поля:
- стабильный `id`;
- `name`, `description`;
- `line_type` (например, mainline, premium, silver series, multipack/other — список расширяемый);
- `status` (candidate / under_review / confirmed / rejected).

Бренд не дублируется строкой в названии. Связь с `Brand` должна быть явной и допускает отдельное расширение до many-to-many, если это понадобится. Не делать `Mainline`, `Premium` и `Silver Series` значениями `Series`.

### `CatalogNode` — размещение в дереве

Одна таблица дерева с `id`, `parent_id`, `node_type`, `sort_order`, `label_override`, `status`, временными метками и необязательными ссылками на сущность. Рекомендуемые типы узлов:
- `root` — корень каталога;
- `product_line` — ссылка на `ProductLine`;
- `year` — годовая папка, с `catalog_year`;
- `group` / `theme` — организационная группа или тема, без собственной идентичности выпуска;
- `series` — ссылка на существующую `Series`;
- `release` — ссылка на существующую `Release`;
- `package` — ссылка на существующую `Package`.

Для ссылочных типов узлов должны использоваться обычные nullable FK-колонки (`product_line_id`, `series_id`, `release_id`, `package_id`) с CHECK-ограничением: заполнена только колонка, соответствующая `node_type`. Это сохраняет ссылочную целостность и позволяет не применять полиморфный `entity_type + entity_id` без FK.

Не добавлять `CatalogNode` для каждой сущности в момент её создания автоматически. Узел дерева — размещение: один `Release` может иметь несколько размещений, а запись `Release` при этом остаётся единственной. Для `Series` действует то же правило.

### Пример Mainline

```text
Каталог
└── Hot Wheels Mainline          [ProductLine]
    ├── 2025                      [year]
    │   ├── HW J-Imports           [Series]
    │   │   ├── Nissan Skyline     [Release]
    │   │   └── Toyota Supra       [Release]
    │   └── HW Dream Garage        [Series]
    └── 2026                      [year]
        └── HW J-Imports           [Series]
            └── ...                [Release]
```

Пример показывает вариант отображения, а не обязательное правило для каждой линейки. Если официальная структура конкретной линейки отличается, её дерево может содержать другие узлы, включая группы или темы.

### Ограничения и проверки

- `parent_id` ссылается на другой `CatalogNode`; удаление родителя с детьми запрещено или требует явного перемещения детей.
- Циклы дерева предотвращаются сервисным слоем и проверяются тестами.
- Правила допустимых пар parent/child проверяются сервисом, а не только UI.
- Годовой узел может содержать только допустимые типы дочерних узлов согласно правилам каталога; Release с неизвестным годом допускается в отдельной группе `Year unknown`, не подставляя выдуманный год.
- Нельзя автоматически менять `Release.catalog_year`, `ReleaseSeries` или идентичность `Release` при перемещении узла.
- `label_override` предназначен только для отображения и не изменяет каноническое имя связанной сущности.
- Перемещения/перегруппировки должны оставлять запись в `ChangeLog` с old/new parent, old/new position и причиной.

## 3. Серии, темы и продуктовые линейки

- `ProductLine`: широкая продуктовая линия/семейство каталога, например Mainline или Premium.
- `Series`: официальная серия/коллекция, к которой относится выпуск; связь уже реализована как many-to-many через `ReleaseSeries`.
- `group` / `theme`: только элементы навигации, если источник/официальная структура использует тематические подгруппы, не требующие самостоятельной сущности.
- Название само по себе не определяет тип: классифицировать по подтверждённому контексту источника и сохранять evidence.

Одна серия может встречаться в нескольких годах/ветвях. Узлы `series` являются размещениями ссылки на `Series`, а не новыми сущностями серии.

## 4. Реальный прототип (origin)

Не переиспользовать `Manufacturer` / `Brand` автоматически для производителей реальных автомобилей: в каталоге игрушек это другая предметная область.

Рекомендуемая отдельная модель `OriginObject`:
- стабильный `id`;
- `object_type` (car, truck, motorcycle, aircraft, fictional, concept, other);
- `make_name`, `model_name`;
- `generation` / `trim_or_variant`;
- `production_start_year`, `production_end_year`;
- `description`, `status`.

Связь `CastingOrigin` — many-to-many с `Casting`, с `role` и `note`. Она необязательна: один Casting может иметь несколько возможных прототипов, а один OriginObject — вдохновлять несколько Casting. Эта связь не объединяет и не разделяет Casting автоматически.

На первом этапе `make_name` можно хранить как наблюдаемое название, подтверждаемое Evidence, не вводя сразу отдельный справочник автомобильных производителей. Выделять `OriginMake` в самостоятельную сущность только при реальной необходимости нормализации и управления алиасами. Не записывать неподтверждённую точную модель или поколение как факт.

## 5. Evidence и аудит

- Добавить типизированные связи Evidence для `ProductLine` и `OriginObject`/ `CastingOrigin` по образцу существующих сущностей.
- Названия, год, серия, принадлежность к линейке и прототип должны сохранять источник и статус проверки.
- Перемещение узла каталога — редакционное действие, а не новое evidence о выпуске.
- Не мигрировать `collection.json` и не заполнять новые сущности данными в рамках реализации схемы.

## 6. Предлагаемая последовательность

1. Согласовать это проектное предложение.
2. Отдельным PR реализовать `ProductLine`, связи с `Brand`, `CatalogNode`, миграцию, проверки и тесты на FK/циклы/перемещения.
3. Следующим небольшим PR реализовать `OriginObject`, `CastingOrigin`, Evidence-связи и тесты.
4. Затем спроектировать API для дерева (получение ветви, поиск, перемещение с аудитом) и только потом подключать UI.
5. Не выполнять импорт или изменение производственного `collection.json` без отдельного решения.

## 7. Критерии приёмки схемы

- Перемещение узла не меняет ID `Release` и его связи с `Casting`/ `Series`.
- Один Release может быть показан в двух ветвях без дублирования Release.
- Невалидные FK и несовпадение node_type с FK блокируются.
- Циклы и недопустимые parent/child отношения отклоняются.
- Удаление узла не удаляет связанную Series/Release/Package.
- Неизвестный год не подменяется выдуманным.
- Значимые перемещения можно восстановить по аудиту.
