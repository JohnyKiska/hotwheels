# Локальная работа с HW Catalog на Windows 10

Статус: согласованная стартовая схема, 2026-11-13.

## Цель

Использовать один внешний HDD как переносимое рабочее хранилище каталога между домашним и рабочим ПК. Не поддерживать две независимые базы и не синхронизировать их вручную.

## Стартовая схема

- Внешний HDD содержит единый каталог данных HW-CATALOG.
- SQLite-файл находится в HW-CATALOG/DATABASE/catalog.db.
- Фотографии и прочие файлы каталога хранятся на том же внешнем диске.
- На обоих ПК запускается локальный экземпляр приложения из актуальной ветки integration/catalog-foundation.
- GitHub хранит исходный код, схемы и историю изменений кода, но не рабочий файл SQLite и не приватные пользовательские данные.
- PostgreSQL и постоянно работающий домашний сервер откладываются до отдельного этапа.

## Переключение между ПК

1. На текущем ПК остановить backend и дождаться завершения процесса.
2. Убедиться, что нет открытых процессов приложения, обращающихся к базе.
3. Выполнить безопасное извлечение HDD средствами Windows.
4. Подключить диск к другому ПК.
5. Проверить букву диска и установить HW_CATALOG_DATA_DIR в путь к HW-CATALOG.
6. Запустить приложение на новом ПК.

**Запрещено** одновременно подключать одну рабочую базу к двум экземплярам приложения, извлекать диск во время работы приложения или редактировать SQLite-файл сторонними средствами при запущенном backend.

## Инициализация

Backend уже документирует команду и формат внешнего хранилища:

```powershell
cd backend
python -m app.init_storage "E:\HW-CATALOG" --label "HW Catalog External HDD"
```

Буква диска в примере условная. Команда инициализации выполняется один раз и не должна запускаться повторно поверх существующего хранилища.

После инициализации на каждом ПК задаётся переменная окружения HW_CATALOG_DATA_DIR, указывающая на корневую папку HW-CATALOG. Точный путь может отличаться, если Windows назначает диску разные буквы.

## Резервное копирование

- Внешний HDD является рабочим носителем, а не резервной копией самого себя.
- Нужна отдельная резервная копия базы и важных файлов на другой физический носитель или в другое независимое хранилище.
- Перед копированием SQLite-базы приложение останавливается либо используется согласованный SQLite backup-механизм. Не копировать открытый файл обычным проводником.
- Резервные копии должны иметь дату и хранить несколько предыдущих поколений.
- Периодически проверять восстановление копии, а не только факт её создания.

## Ограничения и следующий этап

SQLite подходит для начальной разработки и последовательной работы одного пользователя на одном ПК. Внешний HDD может быть медленнее внутреннего SSD, поэтому возможны более долгие операции. Для одновременной работы нескольких пользователей, постоянного сетевого доступа и надёжного круглосуточного сервиса потребуется перейти на PostgreSQL на постоянно включённом сервере.

До такого перехода сохраняем единый формат каталога и не переносим рабочую базу в Git.
