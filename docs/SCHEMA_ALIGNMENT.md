# Сверка визуальной схемы и backend-моделей

**Дата:** 2026-10-29  
**База сравнения:** `main` после PR #56 — `3d31fb1283a1ae5312d546b48d98a63b83141fc4`  
**Источники:** `prototype/catalog-visual/hw-catalog-schema.json`, `backend/app/models.py`, `backend/migrations/versions/*`.

Этот документ — аудит расхождений, а не новая окончательная схема и не разрешение на миграцию производственных данных. Визуальный прототип остаётся демонстрационным; его поля нельзя автоматически считать физической схемой БД.

## Уже представлено в backend

- `Casting` — базовая идентичность конструкции.
- `CastingVariant` — отдельный подтверждаемый вариант конструкции; в визуальной схеме пока не показан отдельным узлом.
- `Release` — выпуск с годом каталога, названием, номером ассортимента и статусом.
- `Series` и `ReleaseSeries` — связь выпуска с несколькими сериями.
- `Source`, `SourceRecord`, `Evidence`, `MediaAsset` — источник, снимок записи, свидетельство и метаданные медиа.
- `Conflict`, `ChangeLog` и таблицы связей — проверка конфликтов и аудит решений.
- `IdentifierType`, `CatalogIdentifier`, `ReleaseIdentifier`, `CastingIdentifier`, `CastingVariantIdentifier` — идентификаторы отделены от внутренних ID и назначаются сущностям через связи.

## Подтверждённые пробелы

| Область | Что есть сейчас | Что нужно спроектировать |
|---|---|---|
| Производитель и бренд | В целевой концепции они разделены, но в `models.py` отдельных моделей нет | Сущности `Manufacturer` и `Brand`, их связь и назначение на Casting/Release без сведения понятий в одно поле |
| Упаковка | В backend нет модели `Package` | Отдельная карточка упаковки с собственным стабильным ID и полями, относящимися именно к упаковке |
| Состав упаковки | Нет таблицы связи Package ↔ Release | Явная many-to-many связь с порядком элементов, ролью/количеством при необходимости и ограничениями целостности |
| Идентификатор упаковки | Типы идентификаторов уже существуют, но назначения для Package нет | Связь Package с `CatalogIdentifier`; товарный номер упаковки не должен смешиваться с номером отдельного автомобиля |
| Свидетельства упаковки | Есть Evidence-связи для Casting, CastingVariant, Release и Series; Package-связи нет | `EvidencePackage` или эквивалентная типизированная связь |
| Продуктовая линейка и дерево каталога | В backend нет отдельных моделей линейки/иерархии каталога | Определить отдельно от Series и от идентичности Release; дерево должно перестраиваться без изменения сущностей |
| Исходный реальный автомобиль | В прототипе есть узел `origin`, в backend модели нет | Отложить до отдельного проектирования; связь с Casting необязательна и не должна сама по себе объединять Casting |
| Поля выпуска | В прототипе указаны цвет, колёса, маркировка днища и фото; в `Release` нет всех этих полей как отдельных колонок | До добавления колонок определить, что является основным полем, вариантом конструкции, медиа или атрибутом со свидетельством |

## Важные инварианты для будущей реализации

1. Внутренний ID не зависит от названия, SKU, UPC или номера Mattel.
2. Один Release относится к одному Casting; выбранный CastingVariant должен принадлежать тому же Casting.
3. Один Release может входить в несколько Series через `ReleaseSeries`.
4. Упаковка и вложенный Release — разные сущности. Номер Mattel/SKU упаковки не заменяет идентификаторы вложенных машинок.
5. Состав Package хранит явный порядок; изменение состава одной упаковки не меняет другую и не удаляет Release.
6. Удаление связей и удаление сущностей — разные действия; внешние ключи должны защищать используемые записи.
7. Значения из источников и решения о спорных полях должны сохранять Evidence и историю.
8. Все новые таблицы получают миграцию Alembic и тесты на связи, ограничения и безопасное удаление.
9. Никаких импортов/миграций из производственного `collection.json` в рамках этого шага.

## Предлагаемый порядок реализации

1. Согласовать минимальную модель Manufacturer/Brand и её связи с Casting/Release.
2. Спроектировать Package, Package ↔ Release с порядком элементов и Package ↔ CatalogIdentifier.
3. Добавить Evidence-связь для Package.
4. Отдельно решить, как моделировать продуктовые линейки/дерево каталога и исходные реальные автомобили.
5. Только после согласования — реализовать модели, миграции и тесты небольшими PR.

## Проверки до слияния PR #52

PR #52 содержит только визуальный прототип и JSON-схему; в проверенных GitHub Actions для его head нет check runs. Пользователь подтвердил независимость состава упаковок в одном ручном сценарии, но это не заменяет автоматических тестов backend-модели Package. Поэтому PR #52 не следует трактовать как реализацию схемы БД и не нужно объединять только на основании того, что прототип визуально работает.
