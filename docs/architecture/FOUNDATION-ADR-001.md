# HW Catalog — архитектурное решение 001

Дата: 2026-11-12  
Статус: принято как целевая временная архитектура; провайдеры размещения ещё не выбраны.

## Контекст

HW Catalog уже содержит визуальный frontend в корне репозитория и backend на FastAPI, SQLAlchemy и Alembic. Backend включает доменные модели, Evidence/Conflict workflows и read-only import preview. Не следует создавать параллельный backend или переносить текущую бизнес-логику в serverless-функции.

Нужно начать с авторизации и администрирования, сохранив возможность перенести приложение с временного облачного размещения на выделенный сервер без переписывания frontend и доменной логики.

## Принятое направление

### 1. Один backend

Сохраняем существующий FastAPI как единственную точку входа для frontend. Все операции с каталогом, пользователями и правами выполняются через версионированный HTTP API (префикс `/api/v1`).

Frontend не обращается к GitHub API напрямую и не содержит секретов.

### 2. Разделение идентификации, прав и каталожных данных

- **Идентификация:** GitHub OAuth Web Application flow. Backend проверяет OAuth callback, получает профиль пользователя и создаёт собственную сессию HW Catalog.
- **Авторизация:** собственные пользователи, роли и разрешения HW Catalog. GitHub username не является ролью и не даёт доступ автоматически.
- **Первый Super Admin:** назначается одноразовой серверной bootstrap-конфигурацией по GitHub numeric user ID. Публичной регистрации с автоматическим повышением прав нет.
- **Каталог:** временно читается и изменяется через серверный GitHub Repository adapter.
- **Служебные данные:** пользователи, роли, сессии, приглашения и аудит хранятся в постоянной SQL-БД. Предпочтительная цель — PostgreSQL, чтобы временное и будущее размещение использовали один движок.

### 3. GitHub Repository adapter

Backend определяет интерфейс хранилища каталога, например:

- `CatalogRepository.list/get`
- `CatalogRepository.create/update/delete`
- `CatalogRepository.commit_changes`

Первая реализация — GitHub adapter. Он работает только на сервере через GitHub App installation token с минимальными правами Contents на один выбранный репозиторий и выбранную ветку.

Изменения записей должны иметь optimistic concurrency control: перед записью проверяется ожидаемый blob SHA/версия. Конфликт параллельных правок возвращается пользователю, а не перезаписывается молча.

GitHub App private key, OAuth client secret и сессионные ключи хранятся только в secrets хостинга. Нельзя помещать их в frontend, репозиторий, localStorage или клиентские конфиги.

### 4. Слой постоянных данных

SQL-БД используется для:
- учётных записей и внешних identity;
- ролей и разрешений;
- сессий и приглашений;
- журнала входов и действий;
- технических настроек, не являющихся частью каталога.

Каталожные JSON-файлы остаются временным источником истины на первом этапе. Не смешивать их с пользовательской БД.

### 5. Перенос на выделенный сервер

Будущее размещение должно запускать те же контейнеры/API и использовать тот же PostgreSQL. При переезде меняются конфигурация, DNS, секреты и адреса сервисов, но не контракты frontend/API и не доменные сервисы.

Позже GitHub adapter заменяется PostgreSQL CatalogRepository после отдельной миграции и сверки данных. Внешние API-контракты при этом сохраняются.

## Роли на старте

Начальный набор ролей:
- `super_admin`: полный доступ, управление системными настройками и ролями;
- `admin`: управление каталогом и пользователями, кроме передачи/снятия super admin;
- `editor`: создание и редактирование каталожных записей;
- `reviewer`: просмотр и проверка/подтверждение изменений;
- `viewer`: чтение.

Роли должны быть реализованы как данные/permissions, а не как проверки GitHub username в коде. Операции удаления, назначения ролей и подтверждения изменений должны иметь отдельные permissions.

## Безопасность и эксплуатация

- OAuth state и PKCE/state validation; секреты только на backend.
- HttpOnly, Secure, SameSite cookies для сессии; защита от CSRF для изменяющих запросов.
- CORS только для известных frontend origins.
- Rate limit на login/callback и административные операции.
- Закрытая регистрация: вход через GitHub сам по себе не создаёт доступ.
- Аудит: actor, action, entity type/id, timestamp, request/correlation ID и результат; не записывать токены и секреты.
- Резервное копирование SQL-БД и проверка восстановления.
- GitHub branch protection и отдельная рабочая ветка для админских изменений.
- Никаких автоматических слияний Casting и никаких обходов текущих правил Evidence/Conflict.

## Этапы реализации

1. Инвентаризировать backend, миграции и тесты; определить совместимость текущей SQL-схемы с PostgreSQL.
2. Зафиксировать API contracts и настройки окружения.
3. Добавить модели User, ExternalIdentity, Role, Permission, UserRole, Session/RefreshSession, Invitation и AuditEvent.
4. Реализовать GitHub OAuth login/logout и bootstrap Super Admin.
5. Добавить RBAC dependencies и тесты доступа на каждом endpoint.
6. Реализовать GitHub App adapter и безопасное сохранение с optimistic concurrency.
7. Подключить текущий frontend к API и сделать страницы входа и администрирования.
8. Развернуть staging, проверить backup/restore, затем подключить production.

## Открытые решения

До реализации OAuth и публикации приложения нужно определить:
- GitHub account/organization, которая будет владельцем GitHub App;
- точный репозиторий и рабочую ветку для записи;
- временный backend host и managed PostgreSQL provider;
- домен или допустимый временный frontend origin.

Выбор конкретного облачного провайдера не должен проникать в код приложения. Все параметры задаются environment variables.
