# Архитектура административного раздела каталога

Статус: проектирование / первый этап реализации  
Базовая ветка: `integration/catalog-foundation`

## Цель

Создать единую административную точку управления каталогом HW Catalog. Админка работает с серверной БД через защищённый API. Локальные JSON-файлы остаются инструментом импорта/экспорта и не являются основным хранилищем изменений.

## Принципы

- Серверная БД является источником истины для рабочих записей каталога.
- Все операции записи требуют активной сессии и соответствующего permission.
- Изменения каталожных сущностей сопровождаются append-only записью в `change_log`: кто, когда, что изменил, причина, старое и новое значение.
- В MVP удаление не предлагается как обычное действие интерфейса. Сначала используем статусы и проверяемые ограничения связей.
- Внутренние UUID остаются неизменными; каталожные номера и артикулы хранятся как идентификаторы, а не как первичные ключи.
- UI не должен напрямую обращаться к БД или хранить применённые изменения только в localStorage.

## Существующая доменная модель

- `Casting`: базовая отливка.
- `CastingVariant`: вариант конструкции отливки.
- `Release`: выпуск конкретного года/ассортимента, связанный с Casting и необязательным CastingVariant.
- `Series` и `ReleaseSeries`: серии и связи выпусков с сериями.
- `IdentifierType`, `CatalogIdentifier`, `CastingIdentifier`, `CastingVariantIdentifier`, `ReleaseIdentifier`: типы идентификаторов и связи артикулов/номеров с сущностями.
- `Evidence`, `SourceRecord`, `MediaAsset`: источники, доказательства и метаданные медиа.
- `ChangeLog`: история изменений.

## Предлагаемая структура интерфейса

Один административный shell с левой навигацией и рабочей областью:

1. Обзор: счётчики и быстрые переходы.
2. Отливки: поиск, карточка, варианты, история.
3. Выпуски: год, название, номер ассортимента, отливка, вариант, серии, идентификаторы.
4. Серии: карточка серии и связанные выпуски.
5. Идентификаторы: типы, значения и привязки.
6. История: журнал изменений по сущности.

Разделы пользователей, модерации и фотографий подключаются к этому shell отдельными этапами, не смешивая их доменную логику с CRUD каталога.

## API MVP

Префикс: `/api/v1/admin/catalog`.

- `GET /overview`: сводные счётчики.
- `GET /castings`: пагинация и поиск по имени/ID/идентификаторам, фильтр статуса.
- `POST /castings`: создать отливку.
- `GET /castings/{id}`: карточка отливки с вариантами, выпусками, идентификаторами и краткой историей.
- `PATCH /castings/{id}`: изменить разрешённые поля с обязательной причиной.
- `POST /castings/{id}/variants`: создать вариант отливки.
- `PATCH /variants/{id}`: изменить вариант.
- `GET /releases`: поиск выпусков по году, названию, номеру, отливке и статусу.
- `POST /releases`: создать выпуск.
- `GET /releases/{id}`: карточка выпуска со связями.
- `PATCH /releases/{id}`: изменить разрешённые поля с обязательной причиной.
- `PUT /releases/{id}/series`: заменить набор связей с сериями атомарно.
- `GET /series`, `POST /series`, `PATCH /series/{id}`: управление сериями.
- `GET /history/{entity_type}/{entity_id}`: история изменений.

Каждый endpoint проверяет разрешение отдельно:
- чтение: `catalog.read`;
- создание: `catalog.create`;
- изменение: `catalog.update`;
- удаление, если оно будет добавлено позднее: `catalog.delete`.

Для записи UI передаёт `reason`. Actor берётся только из аутентифицированной сессии, не из тела запроса. CSRF-проверка применяется ко всем изменяющим запросам.

## Валидация и защита данных

- Проверять существование связанных сущностей до записи.
- Сохранять DB constraints как последний рубеж защиты.
- Проверять принадлежность CastingVariant той же Casting при создании/изменении Release.
- Сохранять уникальность релиза по существующему ключу Casting + год + assortment number.
- Не удалять сущности, на которые ссылаются выпуски, доказательства, конфликты или идентификаторы.
- Не принимать `actor_id`, `actor_type`, готовые `old_values` или `new_values` от клиента.
- Для PATCH логировать только реально изменившиеся поля.
- Для набора связей использовать одну транзакцию.

## Первый пользовательский сценарий

Администратор открывает «Каталог» → находит отливку → просматривает её варианты и выпуски → редактирует поле с указанием причины → сохраняет → видит результат и новую запись в истории.

## Вне первого этапа

- Управление пользователями и ролями.
- Решение конфликтов и модерация.
- Загрузка и подбор фотографий/eBay listings.
- Массовые операции и импорт непосредственно из админки.
- Физическое удаление записей.

Эти функции будут добавляться после того, как защищённый CRUD и базовый административный интерфейс пройдут тестирование.
