# Модель общего каталога Hot Wheels

## Цели

- Исходные списки `*_collection.txt` и `*_series.txt` — это авторская классификация-источник, а не неизменяемая схема.
- Структуру можно перестраивать: переносить группу целиком, переносить отдельные элементы или добавлять дополнительные группировки.
- Перестройка и переименование не меняют идентификаторы сущностей и не затрагивают личную коллекцию.
- Совпадающие названия в разных направлениях изначально остаются отдельными записями.
- Модели автомобилей можно добавлять позже, не меняя принцип организации групп.

## Принцип хранения

Разделяем **сущность**, **связь в дереве**, **происхождение** и **личные экземпляры**.

### 1. Сущности каталога — `catalog_nodes`

Каждая группа, коллекция, серия или модель получает постоянный ID.

```json
{
  "id": "series:car-culture",
  "kind": "series",
  "name": "Car Culture",
  "attributes": {},
  "createdAt": "2026-10-23T00:00:00Z",
  "updatedAt": "2026-10-23T00:00:00Z"
}
```

- `id` — постоянный идентификатор; не генерируется заново при перемещении или переименовании.
- `kind` — тип сущности: `group`, `collection`, `series`, позднее `model`.
- `name` — отображаемое название.
- `attributes` — расширяемые свойства без необходимости менять базовую структуру.

Не используем название как уникальный ключ: одинаковые названия допустимы.

### 2. Иерархия — `catalog_edges`

Родительские связи хранятся отдельно от самих сущностей.

```json
{
  "id": "edge:mainline-premium",
  "parentId": "group:premium",
  "childId": "group:mainline",
  "relation": "contains",
  "order": 10
}
```

Это позволяет переместить Mainline под Premium, не переписывая записи Mainline и её дочерних элементов. Для частичного переноса меняются только связи выбранных элементов.

Правила целостности:
- запрещать циклы в иерархии;
- не допускать повторения одной и той же связи;
- удаление связи не удаляет саму сущность;
- удаление сущности и каскадное удаление её содержимого — отдельная явно подтверждаемая операция;
- при переносе группы проверять, не создаёт ли новое положение цикл.

Если сущность должна отображаться в нескольких местах, допускаются несколько связей. Это не создаёт копию сущности.

### 3. Исходная классификация — `catalog_sources` и `source_memberships`

Исходные файлы сохраняются как источник данных, отдельно от текущего представления каталога.

```json
{
  "id": "source:mainline-series",
  "fileName": "mainline series.txt",
  "direction": "Mainline",
  "sourceType": "series-list"
}
```

Пример членства в исходном списке:

```json
{
  "sourceId": "source:mainline-series",
  "nodeId": "series:example",
  "sourceLabel": "Example Series",
  "sourceParentLabel": "Mainline",
  "position": 12
}
```

Исходное членство — это запись о происхождении/первоначальной классификации. Оно не меняется автоматически, когда редактор перестраивает текущую иерархию. Благодаря этому исходную структуру можно показать или восстановить.

Поскольку исходные файлы содержат отдельные списки коллекций и серий, а точные связи между ними не всегда заданы, связи нельзя угадывать: неизвестное отношение остаётся неустановленным до ручного сопоставления.

### 4. Личная коллекция — отдельный слой

Личные экземпляры с полями вроде `toyNum`, `colNum`, `status`, `price`, `comment` хранятся отдельно. По мере появления общего каталога личная запись сможет ссылаться на `catalogNodeId`, но её личные поля не переносятся в общую базу.

Существующий `collection.json` нельзя автоматически перезаписывать в рамках импорта или перестройки каталога.

### 5. Черновики и применение изменений

- Редактор изменяет черновую копию структуры.
- Черновик автоматически сохраняется локально и восстанавливается после перезагрузки страницы.
- Кнопка «Применить» проверяет целостность, затем применяет изменения к рабочей структуре.
- «Отменить черновик» отбрасывает только незавершённые изменения.
- Для статического сайта локальное автосохранение действует в этом браузере; для общего доступа и синхронизации между пользователями потребуется серверное хранилище и авторизация.

## Пример: Mainline → Premium

**Перенести целиком:** добавить связь `Premium → Mainline`. Идентификаторы и записи не меняются.

**Перенести частично:** перенести выбранные дочерние связи под Premium; остальные оставить под Mainline.

**Создать дополнительное представление:** добавить вторую связь к существующему элементу. Не копировать его запись и не объединять сущности только по совпадению названия.

## Импорт исходных списков

1. Сохранить исходные текстовые файлы без изменений.
2. Создать отдельные сущности для каждого названия в контексте исходного списка; одинаковые названия из разных направлений пока не объединять.
3. Записать происхождение каждой сущности.
4. Связи между группами, коллекциями и сериями создавать только там, где они подтверждены источником или вручную.
5. Перед массовым импортом проверить пилотную выборку и показать неразрешённые связи для ручной классификации.

## Важное ограничение текущего этапа

Эта схема описывает целевую модель данных. Она сама по себе не реализует редактор, синхронизацию или базу моделей. Сначала нужно импортировать названия и происхождение, проверить их, а затем подключать интерфейс редактирования и слой моделей.
