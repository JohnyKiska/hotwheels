# Hot Wheels — точка входа для нового чата

**Назначение:** восстановить контекст проекта в новом чате ChatGPT, другой модели или другом аккаунте без повторного объяснения концепции.

> Документы в GitHub — переносимый источник контекста. Память ChatGPT не является обязательной для продолжения работы. Если другой аккаунт не имеет доступа к репозиторию, передай ему ссылки/копии этих документов или предоставь доступ к репозиторию.

## Прочитать в таком порядке

1. [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md) — цель проекта, модель данных, закреплённые правила и ограничения.
2. [docs/CURRENT_STATE.md](docs/CURRENT_STATE.md) — проверенное состояние кода, веток, PR и тестов.
3. [docs/ROADMAP.md](docs/ROADMAP.md) — этапы и последовательность дальнейшей работы.
4. [docs/SESSION_HANDOFF.md](docs/SESSION_HANDOFF.md) — ближайшие шаги для продолжения с места остановки.

## Разделение рабочих чатов

- **Разработка импортеров HW Catalog:** проектирование и реализация семейства специализированных импортеров. Стартовый обработчик — Mainline Importer, затем Premium Importer и другие линейки.
- **Backend и тестирование:** API, модели, миграции, интеграция, автоматические и ручные проверки.
- **Визуал админки:** отдельный поток интерфейса и UX. Не переносить вопросы визуального дизайна в поток импортеров/backend без необходимости.

Новый чат по импортерам должен начать с SESSION_HANDOFF.md и аудита исходных форматов/старого importer.html. Архитектурное решение о семействе специализированных импортеров уже принято; конкретные правила обработки каждой линейки ещё предстоит спроектировать.

## Обязательные правила для помощника

- Сначала прочитай эти документы, затем проверь актуальные ветки, Pull Requests, CI и файлы GitHub. Не полагайся только на даты или формулировки в документации.
- Считай документированное решение закреплённым, пока пользователь явно не пересмотрел его.
- Не утверждай, что файл, тест или workflow проверен, если фактически не проверил его.
- Различай **реализовано**, **проверено вручную**, **проверено автоматическими тестами**, **запланировано** и **неизвестно**.
- Не изменяй main, производственный collection.json или другие производственные данные без отдельного согласования.
- Не запускай миграцию существующего collection.json в новую модель данных без отдельного решения пользователя.
- Перед исправлением сначала изучи текущую реализацию и тесты. Предпочитай небольшие изменения с ясными критериями приёмки.
- Не объединяй похожие записи между разными исходными файлами автоматически.
- При конфликте источников сохраняй свидетельства и отправляй существенные противоречия на ручную проверку.
- Если документы расходятся с кодом, зафиксируй расхождение и выясни, какое состояние актуально; не исправляй документы догадкой.
- При завершении каждого рабочего сеанса обновляй docs/CURRENT_STATE.md и docs/SESSION_HANDOFF.md, а при изменении плана — docs/ROADMAP.md.

## Как обновлять документы

После значимого изменения укажи:
- дату;
- ветку и PR;
- изменённые файлы;
- что сделано;
- какие проверки действительно прошли;
- что осталось;
- точный следующий шаг и критерий готовности.

Не записывай секреты, токены, пароли или приватные пользовательские данные в эти файлы.

## 10. Координация и границы рабочих чатов

В проекте действует разделение по зонам ответственности. Каждый чат выполняет свою прямую задачу и не подменяет собой другие направления.

| Рабочий чат | Зона ответственности |
|---|---|
| Координация HW Catalog | Распределение задач, контроль этапов, передача контекста, устранение пересечений |
| Архитектура и модель данных | Сущности, связи, идентификация Casting/Release, Evidence, бизнес-правила и изменения схемы |
| Разработка импортеров | Mainline, Premium и другие специализированные обработчики, парсеры, импортные сценарии |
| Backend и тестирование | API, ORM-модели, миграции, интеграция, общие backend-тесты и регрессии |
| Источники и каталогизация | Фотографии, блистеры, ALLHW, каталоги, сопоставление машинок и сбор свидетельств |
| Визуал и админка | UI, UX, карточки, таблицы, навигация и внешний вид |
| Инфраструктура | GitHub Actions, CI/CD, окружение, расписания и развёртывание |

### Правила маршрутизации

1. Чат сначала определяет, к какой зоне относится задача.
2. Если задача относится к другой зоне, чат не начинает самостоятельную реализацию и не меняет чужие компоненты.
3. Чат объясняет причину передачи и указывает целевой рабочий чат.
4. При передаче формируется краткий контекст: проблема, уже проверенные факты, затронутые файлы, принятые решения и ожидаемый результат.
5. Если задача затрагивает несколько зон, сначала передаётся вопрос владельцу архитектурного решения, затем согласованная работа направляется исполнителю и проверяющему.
6. Общие правила проекта и закреплённые архитектурные решения обязательны для всех чатов.
7. Рабочий чат может обнаружить проблему за пределами своей области, но не должен молча исправлять её в чужой зоне.
8. Не создавать параллельные реализации одной задачи в разных чатах.

### Разделение ответственности на практике

- Архитектура определяет, как должны идентифицироваться Casting и Release. Импортер реализует утверждённые правила.
- Источники и каталогизация устанавливают факты по фотографиям, блистерам и каталогам. Импортер решает, как технически обработать соответствующие данные.
- Backend реализует общие API, модели и миграции. Импортер использует согласованные интерфейсы.
- Тестирование проверяет общую интеграцию и регрессии. Каждый рабочий поток отвечает за свои профильные проверки.
- Визуал админки определяет представление информации, но не меняет семантику данных самостоятельно.
- Инфраструктура обеспечивает выполнение и доставку кода, но не принимает за архитектуру продуктовые решения.

### Координационный чат

Координация не заменяет специализированную работу. Её задача — определить владельца вопроса, сформировать последовательность действий, отслеживать зависимости и синхронизировать документацию.

В конце значимого этапа рабочий чат передаёт результаты координатору для обновления общего состояния проекта и передачи контекста.

Этот раздел дополняет и уточняет ранее описанное разделение рабочих потоков.
